# .pidly

How this tracker works. Generated by `pidly agents` — edit the tracker, not
this file. Read it when you need a rule you do not already know; the summary
in AGENTS.md covers the common path.

## Shape

A ticket is a **directory**. Its name is its number. `info` inside it is what
is known about it. Nesting a ticket inside another makes it a subtask.

**State is location.** A ticket is open if it sits directly in its container,
closed if it sits in that container's `c/`. Nothing else records state.

```
.pidly/
  schema.md        project fields
  7/
    info           ticket 7, open
    12/
      info         ticket 12, an open subtask of 7
    c/
      13/info      ticket 13, a finished subtask of 7
  c/
    4/info         ticket 4, finished, top level
```

Numbers are unique across the whole tracker and **never reused**. A path is
made of ticket numbers and `c`, so `.pidly/7/12/` is ticket 12 under 7.

## The info file

```
claim:                     1  empty, or who holds it
needs: 3 8                 2  tickets that must close before this starts
title: Short human title   3
effort: M                  4  project fields, defined in schema.md
handoff: where I got to    5  ...as many as the schema declares, or none
                           6  one blank line
The body, from here        7  ...to the end of the file
```

Read only as far as you need:

| want | read |
|---|---|
| can I take this? | `sed -n 1,2p info` |
| a listing line | `sed -n 3p info` |
| project fields | `awk 'NR>3 { if ($0=="") exit; print }' info` |
| the body | `awk 'b { print } !b && $0=="" { b=1 }' info` |

Nothing records where the body starts or ends. It runs to the end of the
file, and the fields stop at the first blank line — which is ahead of the
body, so nothing you write in a body can be mistaken for the boundary.
Appending to a body needs no bookkeeping.

## Finding work

```sh
pidly list        # ready work: unclaimed and unblocked
pidly list -a     # every open ticket, with its state
pidly tree        # the hierarchy, closed tickets marked [x]
pidly check       # report anything wrong; changes nothing
```

By hand, or when pidly is not installed:

```sh
find .pidly -type d -name c -prune -o -name info -print
```

`-prune` is what keeps this from walking finished work. A ticket is
**takeable** when line 1 is empty and every number on line 2 resolves to a
directory whose path contains `/c/`.

Resolve those numbers with **one traversal**, not one `find` per dependency:
build a number-to-path map from a single `find .pidly -type d` and answer
every lookup from it. On a 2000-ticket tree the difference is 26.5s against
2.0s.

## Claiming

```sh
PIDLY_PID=$$ pidly claim 7     # $$ is your agent's process, not the CLI's
pidly status 7
pidly release 7
```

Export `PIDLY_PID` once for the life of your agent. A release only succeeds
for the process that made the claim, so claiming and releasing from separate
invocations have to agree on who you are.

A claim records `<pid>.<starttime>@<runtime>`. The start time is what stops a
recycled pid from looking like the original process; the runtime is boot id,
uid and pid namespace, so a pid is only ever checked against the process
table it came from.

If you have no process anyone here can check — a cloud session, a CI job —
claim with a lease and renew by claiming again before it expires:

```sh
PIDLY_AGENT=$SESSION_ID PIDLY_LEASE=2h pidly claim 7
```

A claim resolves to one of:

| state | meaning |
|---|---|
| `expired` | the lease ran out; anyone may take it |
| `live` | same runtime, process is there |
| `dead` | same runtime, process positively is not |
| `unverifiable` | another runtime, lease still good |

Only `free` and `expired` can be claimed. Only `dead` can be cleared, with
`pidly reap`. **Never treat `unverifiable` as dead** — that puts two agents
on one ticket.

Claiming rewrites line 1, so it is the one operation that is not safe to do
by hand while other agents are running: `pidly claim` serializes it behind a
lock. Everything else here is safe with `find`, `sed` and `mv`.

### Handing off

If you stop before finishing, say where you got to:

```sh
pidly release -m "Parser works; lexer still fails on nested quotes." 7
```

That lands in the `handoff` field, and `pidly claim` prints it to whoever
picks the ticket up next. One line — anything longer belongs in the body. It
is overwritten by the next handoff, not accumulated, so it always describes
the most recent stop.

## Creating

A project with no tracker starts one with `pidly init`, which seeds this
file, `schema.md` and the ignore rules. Re-running it refreshes the generated
files and leaves `schema.md` alone.

The next number is the **highest number anywhere in the tracker plus one**,
counting closed tickets. There is no counter file. Make the directory inside
the parent, or in `.pidly/` for a top-level ticket, and write the four header
lines:

```sh
mkdir .pidly/7/14
printf 'claim:\nneeds:\ntitle: %s\n\n%s\n' "Do the thing" "Why." \
  > .pidly/7/14/info
printf '%s %s\n' "$(head -c8 /dev/urandom | od -An -tx1 | tr -d ' ')" \
  "Do the thing" > .pidly/.n/14
```

That last file is the **number registry**. It is what makes two branches
issuing the same number a merge conflict instead of a silent duplicate, so a
ticket created by hand needs one too. `pidly init` backfills any that are
missing, and `pidly new` writes it for you along with the lock that stops two
agents picking the same number.

## Delegating to a subagent

A subagent usually shares its parent's process — under Claude Code, a Bash
call from a subagent reports the same `CLAUDE_PID` as the lead agent. So a
pid cannot tell them apart: two claims, one pid, both live. **A subagent
claims as an agent, with a lease**, the same way a cloud agent does:

```sh
PIDLY_AGENT=sub-review-parser PIDLY_LEASE=1h pidly claim 19
```

The lead agent creates the ticket and passes the number down, because it
writes the subagent's prompt:

```sh
pidly new -p 7 "Review the parser changes"     # prints 19
# ...then include "your ticket is 19" in the subagent's instructions
```

When the subagent finishes it leaves a handoff and releases; the lead reads
that and decides whether to close. If the subagent dies, the lease expires
and the ticket frees itself.

**Write down what the subagent found before the context is gone.** Its
output is otherwise ephemeral: it lands in the lead agent's context, gets
summarised, and disappears. Findings go in the body of the ticket the
subagent worked on. Appending to a body is just appending.

If the result is a standalone artifact — a review, a benchmark — put it
where artifacts live in the repo and reference the path from the body. It is
usually about the code rather than about the ticket, so it belongs next to
the code, where everyone finds it and where closing the ticket does not
archive it.

Not a ticket of its own. One created and closed in the same breath is a log
entry wearing a ticket costume, and it spends a number that can never be
reused.

**Not every subagent deserves a ticket.** A lookup or a search does not.
Numbers are never reused and tickets are never deleted, so a ticket per
subagent call is permanent noise — and an open child blocks its parent from
closing, so it does active harm. Open one when the work is a unit you would
want to see in the tracker tomorrow.

## Closing and reopening

Closing is a move into the container's `c/`:

```sh
pidly close 12    # or: mkdir -p .pidly/7/c && mv .pidly/7/12 .pidly/7/c/
pidly reopen 12
```

A ticket **cannot close while it has children outside its own `c/`**. That is
what keeps a finished tree from containing live work.

`reopen` moves it back, and **cascades upward**: if a closed ancestor holds
it, that ancestor reopens too, one move per level. If a subtask needs redoing
then its parent is not finished either. Reopening does not cascade downward,
and does not reopen tickets that `needs` it.

Reopen also takes a ticket that is *already open* but sits inside a closed
ancestor — a state a hand-run `mv` can leave behind, and one `check` reports.
The cascade is its repair.

## Rules that will bite you

- **Never delete a ticket.** Numbers are never reused, and deleting one lets
  its number be issued again to something else. Close it instead.
- **`needs` holds numbers, never paths.** A number is permanent; a path
  changes every time a ticket is closed or re-parented.
- **Parents and dependencies are different things.** `needs` blocks starting;
  children block closing. Neither implies the other, and a parent is never an
  implicit dependency of its own children.
- **Leave a handoff when you stop early.** A dropped claim with no note makes
  the next agent reconstruct your progress from the diff.
