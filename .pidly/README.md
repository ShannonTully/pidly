# .pidly

How this tracker works. Generated by `pidly agents` — edit the tracker, not
this file. Read it when you need a rule you do not already know; the summary
in AGENTS.md covers the common path.

## Shape

A ticket is a **directory**. Its name is its number. `info` inside it is what
is known about it. Nesting a ticket inside another makes it a subtask.

**State is location.** A ticket is open if it sits directly in its container,
closed if it sits in that container's `c/`. Nothing else records state.

```
.pidly/
  schema           the project's fields, one stanza each
  7/
    info           ticket 7, open
    12/
      info         ticket 12, an open subtask of 7
    c/
      13/info      ticket 13, a finished subtask of 7
  c/
    4/info         ticket 4, finished, top level
```

Numbers are unique across the whole tracker and **never reused**. A path is
made of ticket numbers and `c`, so `.pidly/7/12/` is ticket 12 under 7.

## The info file

```
claim:                        1  empty, or who holds it
needs: 3 8                    2  tickets that must close before this starts
title: Short human title      3
created: 2026-09-16T21:43:59Z 4  when the ticket was made
updated: 2026-09-17T08:02:11Z 5  when pidly last wrote to it
effort: M                     6  project fields, declared in .pidly/schema
handoff: where I got to       7  ...as many as the schema declares, or none
                              8  one blank line
The body, from here           9  ...to the end of the file
```

`created` and `updated` are pidly's own fields rather than the project's, so
they are valid whether or not the schema mentions them. Both are ISO-8601
UTC, which sorts lexically. `created` records one event and nothing touches
it again; `updated` records **an event on this ticket** — `claim`, `release`,
`edit`, `set`, `reap`. Each of those is one agent doing one thing to one
ticket, which is what the stamp is asked about.

A write that landed on every ticket at once does not bump it: `pidly fields`
adds a slot to the whole tracker and says nothing about any one piece of
work, and stamping all of them would flatten `list --stale` on the day it
ran. Nor do `close` and `reopen`, which move a directory without opening the
file, and nor can an edit made by hand or with `sed`, which cannot call
anything at all.

So `updated` is not the file's mtime and not a record of every write. It is
*when something last happened to this ticket, as far as pidly saw*. Use
`pidly edit` if you want the stamp to follow your own edit.

Read only as far as you need. The right-hand column is what the file is, and
it keeps working in a checkout where pidly was never installed; the left is
what to type when it was.

| want | command | read |
|---|---|---|
| the whole ticket | `pidly show 7` | `cat info` |
| where ticket 7 is | `pidly show -p 7` | `find .pidly -type d -name 7` |
| can I take this? | — | `sed -n 1,2p info` |
| a listing line | — | `sed -n 3p info` |
| project fields | `pidly show -F 7` | `awk 'NR>3 { if ($0=="") exit; print }' info` |
| one field of one ticket | `pidly show -f effort 7` | `sed -n 's/^effort: //p' info` |
| one field of every ticket | `pidly field effort` | a loop over the above |
| the body | `pidly show -b 7` | `awk 'b { print } !b && $0=="" { b=1 }' info` |

`show -p` is the one every hand idiom above needs first, and it is why the
other rows can be written as a single `sed` against `info` rather than a
`find` each. A resolved path is yours to read; it is not a licence to write
lines that a command owns — see `set` for `title` and `needs`, and
`reparent` for the directory itself.

Nothing records where the body starts or ends. It runs to the end of the
file, and the fields stop at the first blank line — which is ahead of the
body, so nothing you write in a body can be mistaken for the boundary.
Appending to a body needs no bookkeeping.

## The schema

`.pidly/schema` declares the project's fields, one stanza per field,
separated by a blank line, in the order `pidly new` writes them:

```
field: effort
match: S|M|L
note: rough size

field: area
required: yes
match: format|cli|docs
note: which part of the project
```

`field:` opens a stanza. `required: yes` means a ticket is not valid until
the field has a value. `match:` is a POSIX ERE the value is tested against,
**anchored** — pidly asks `^(<pattern>)$`, so `S|M|L` cannot half-match
`M extra`. No `match:` means anything, an empty value is never matched
against one, and `note:` is one line.

Everything after `match: ` is the pattern, so `|`, spaces, brackets and
braces need no escaping. That is the reason this is not a markdown table:
a table separates its cells on `|` and an ERE alternates on `|`.

Read it the way everything here is read:

```sh
awk '$1 == "field:" { print $2 }' .pidly/schema
awk '$1=="field:" { cur=$2 } $1=="required:" && $2=="yes" { print cur }' \
    .pidly/schema
```

Two things the implementation is stuck with, and so are you:

- **Patterns go through `grep -E`, never awk.** mawk has no interval
  expressions — `[0-9]{4}` matches `2026` under `grep -E` and does not under
  mawk, in a literal `/re/` or a dynamic `$0 ~ p` — and gawk differs again.
  A pattern's meaning must not depend on which awk is installed.
- **Keep to POSIX ERE.** `\d`, `\w`, `\s`, `\b` and `(?...)` are PCRE.
  Some greps take them anyway — ugrep does — so a pattern written against
  whatever is installed here can mean something else on the next machine.
  `pidly check` reports them rather than trusting the local tool, along with
  a pattern grep cannot compile and a stanza with no `field:`.

`claim:`, `needs:` and `title:` are lines 1, 2 and 3 of every ticket: they
belong to the format, not to the project, and are not declared here. Neither
are `created:` and `updated:`.

pidly declares those in the same language, compiled into the script:

```
line: 1
field: claim
match: [0-9]+(\.[0-9]+)?@[0-9a-z]+\.u[0-9]+(\.n[0-9]+)?( [0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z)?|[^ @]+@- [0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z
note: <pid>.<starttime>@<runtime>, alone or followed by a lease expiry, or <agent>@- <expiry>

line: 2
field: needs
match: [0-9]+( [0-9]+)*
note: ticket numbers separated by spaces

line: 3
field: title
required: yes
match: .+
note: one line, and never empty

field: defer
note: why this is not work yet, and what would make it work

field: created
match: [0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z
note: an ISO-8601 UTC timestamp

field: updated
match: [0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z
note: an ISO-8601 UTC timestamp
```

That is the whole grammar of a ticket's header, in one place, and `check`
applies it to every ticket. `line:` is what says a field is read by position
rather than by name — the takeable scan reads lines 1 and 2 by number — and
it is the one key your schema may not use. Declaring any of these names in
`.pidly/schema` is a finding too: a project that could redeclare `title`
could say it may be empty, and every listing prints it.

A finding about one of these shows the `note:` rather than the pattern,
because the pattern is not in a file you can open:

```
7: claim is 'garbage', which is not <pid>.<starttime>@<runtime>, alone or
   followed by a lease expiry, or <agent>@- <expiry>
```

## Telling Claude Code about it

```sh
pidly claude      # writes .claude/skills/pidly/SKILL.md, the slash commands
                  # and, if there is none, a settings.json that allows the
                  # read-only commands without a prompt
```

The skill is the **workflow** — claim before starting, release with `-m` when
stopping early, close when done — and it points back at this file for the
rules rather than restating them. The AGENTS.md block is the format; the
skill is the loop. `/pidly-next`, `/pidly-mine` and `/pidly-drop` are the
three things worth one keystroke.

Both are generated, and `pidly check` compares them against what would be
generated now, for the reason every copy here is compared: a copy that drifts
is worse than no copy. There are no hooks: enforcement is the operator's, and
a hook that blocks a tool call is a strong thing to install on someone's
behalf.

`pidly man` is the same idea for the CLI rather than for this tracker. It
writes the manual page to stdout, generated from the text `pidly help`
prints, so the two cannot disagree:

```sh
pidly man > docs/pidly.1
```

Most projects never want one — the page documents pidly, not your tracker,
and `check` says nothing unless `docs/pidly.1`, `man/pidly.1` or `pidly.1`
already exists. Where one does, it is compared like everything else here.
Nothing in the page is dated or versioned: a page carrying today's date would
differ from yesterday's committed copy every morning, and the drift would be
the clock rather than the content.

Not an MCP server. That is a process, and the premise is that there is
nothing to run — Bash already reaches the CLI.

## Finding work

```sh
pidly list             # ready work: unclaimed and unblocked
pidly list -a          # every open ticket, with its state
pidly list --stale 7d  # open work pidly has not written to in that long
pidly field effort     # one field across every open ticket, - where it is unset
pidly tree             # the hierarchy, closed tickets marked [x]
pidly check            # report anything wrong; changes nothing
```

`field` prints rows rather than a summary, so the spread of one is `pidly
field effort | awk '{print $2}' | sort | uniq -c`, and the tickets missing it
are the `-` rows. It reads the field by name in a single pass over the
tracker: a loop that runs a command per ticket costs 17.4s over 2000 tickets
where this costs 0.44s.

A ticket with a `defer:` is **not ready**: it is open work that nobody should
pick up yet, and the field says what would change that.

```sh
pidly set 34 defer "picking among unblocked tickets needing a sort"
pidly list -a    # 34  deferred  Priority as a header line (until picking ...)
pidly set 34 defer               # the trigger fired: it is ready again
```

`list` leaves it out, `list -a` shows it with its trigger, and `claim` prints
the trigger rather than refusing — a blocker is a fact about the tracker, and
this is an opinion about the work, so the person asking gets to decide. The
trigger lives on the ticket instead of in a design document nobody reads
while choosing what to do next.

`defer` is pidly's field, like `created` and `updated`: it is not declared in
`.pidly/schema`, `new` does not stub it, and `fields` does not add it. Only
`list` and `claim` read it.

`--stale` takes the same durations a lease does — `90s`, `30m`, `2h`, `7d` —
and lists the oldest first. A ticket with no `updated` line is listed too,
with `-` for the date: it cannot be shown to be fresh, and the question is
what has been forgotten.

By hand, or when pidly is not installed:

```sh
find .pidly -type d -name c -prune -o -name info -print
```

`-prune` is what keeps this from walking finished work. A ticket is
**takeable** when line 1 is empty and every number on line 2 resolves to a
directory whose path contains `/c/`.

Resolve those numbers with **one traversal**, not one `find` per dependency:
build a number-to-path map from a single `find .pidly -type d` and answer
every lookup from it. On a 2000-ticket tree the difference is 26.5s against
2.0s.

## Claiming

```sh
PIDLY_PID=$$ pidly claim 7     # $$ is your agent's process, not the CLI's
pidly status 7
pidly release 7
```

Export `PIDLY_PID` once for the life of your agent. A release only succeeds
for the process that made the claim, so claiming and releasing from separate
invocations have to agree on who you are.

A claim records `<pid>.<starttime>@<runtime>`. The start time is what stops a
recycled pid from looking like the original process; the runtime is boot id,
uid and pid namespace, so a pid is only ever checked against the process
table it came from.

If you have no process anyone here can check — a cloud session, a CI job —
claim with a lease and renew by claiming again before it expires:

```sh
PIDLY_AGENT=ci-run-4821 PIDLY_LEASE=2h pidly claim 7
```

`ci-run-4821` is an example, not a variable: pick any name you will
recognise when you read the claim back, and it is recorded verbatim. An
empty `PIDLY_AGENT` is an error rather than a fallback to your pid, because
it almost always means a variable that does not exist.

A claim resolves to one of:

| state | meaning |
|---|---|
| `expired` | the lease ran out; anyone may take it |
| `live` | same runtime, process is there |
| `dead` | same runtime, process positively is not |
| `unverifiable` | another runtime, lease still good |

`pidly list` agrees with all of this as far as it can without asking the
process table: an **expired** lease is offered as ready — it is takeable, and
a listing that hid it was hiding work — and `list -a` says whose lease ran
out. A **dead** claim still reads `claimed` there, because telling a dead pid
from a live one is a process per ticket, and `claim` refuses it anyway until
`reap` clears it. So the two never disagree about what you can take.

Only `free` and `expired` can be claimed. Only `dead` can be cleared:

```sh
pidly reap 7      # clear a dead claim on one ticket, and say why if it will not
pidly reap        # sweep the whole tracker, closed work included
```

**Never treat `unverifiable` as dead** — that puts two agents on one ticket,
and `reap` will not do it for you. It refuses a live claim, an unverifiable
one, and an expired lease, which needs no clearing because it is already
takeable. A stale `.lock` needs no clearing either: it names a local process,
and the next command to want the lock breaks it.

Claiming rewrites line 1, so it is the one operation that is not safe to do
by hand while other agents are running: `pidly claim` serializes it behind a
lock. Everything else here is safe with `find`, `sed` and `mv`.

### Handing off

If you stop before finishing, say where you got to:

```sh
pidly release -m "Parser works; lexer still fails on nested quotes." 7
```

That lands in the `handoff` field, and `pidly claim` prints it to whoever
picks the ticket up next. One line — anything longer belongs in the body. It
is overwritten by the next handoff, not accumulated, so it always describes
the most recent stop.

## Creating

A project with no tracker starts one with `pidly init`, which seeds this
file, `schema` and the ignore rules. Re-running it refreshes the generated
files and leaves `schema` alone.

```sh
pidly new -f effort=M -f area=cli "Do the thing"     # body from stdin
```

`-f` sets a project field. `pidly new` writes a line for **every field the
schema declares**, in declaration order, whether or not it has a value: an
empty slot shows what the project expects without opening the schema, and it
makes two tickets line up when they are diffed. A field marked `required: yes`
must have a value — `new` refuses without one, and `check` reports a ticket
whose required field is empty as well as one where it is missing. Required
means a value, because an empty field and an absent one read the same to
anything that goes looking.

The uniform blocks do **not** make line numbers dependable. Read a field by
name: that is right for a ticket written under any schema, where counting
lines is right only until the table changes, and then silently wrong for
exactly the old tickets worth reading.

The next number is the **highest number anywhere in the tracker plus one**,
counting closed tickets. There is no counter file. Make the directory inside
the parent, or in `.pidly/` for a top-level ticket, and write the three
header lines, and the stamps:

```sh
mkdir .pidly/7/14
now=$(date -u +%Y-%m-%dT%H:%M:%SZ)
printf 'claim:\nneeds:\ntitle: %s\ncreated: %s\nupdated: %s\n\n%s\n' \
  "Do the thing" "$now" "$now" "Why." > .pidly/7/14/info
printf '%s %s\n' "$(head -c8 /dev/urandom | od -An -tx1 | tr -d ' ')" \
  "Do the thing" > .pidly/.n/14
```

Leaving the timestamps out is not an error — `pidly init` fills in missing
ones from git, or the file's mtime outside a repo, the same way it backfills
a missing registry entry.

That last file is the **number registry**. It is what makes two branches
issuing the same number a merge conflict instead of a silent duplicate, so a
ticket created by hand needs one too. `pidly init` backfills any that are
missing, and `pidly new` writes it for you along with the lock that stops two
agents picking the same number.

## Editing

```sh
pidly edit 7                 # $EDITOR on info, read for structure before it lands
pidly edit -b 7 < body.md    # replace the body from stdin
pidly edit -a 7 <<'EOF'      # append to it: findings, results, where you got to
Reviewed the parser: the lexer loses nested quotes at depth 2.
EOF
pidly edit -r "the old sentence." -w "the new one." 7   # one passage
```

`-r` matches **literally, not as a regex**, and the text must appear **exactly
once**. A body quotes shell, awk and patterns constantly, so a caller made to
escape what they can see in front of them will get it wrong; and a passage
that appears twice is a caller who means one of them and cannot say which.
Both cases are refused rather than guessed at.

It exists because `-b` replaces the whole body, so changing one paragraph
without an editor meant reconstructing all of it and piping it back — and
anything left out was gone. That failure is silent: a truncated body is a
legal ticket, `check` has nothing to say about it, and the loss surfaces when
someone next reads the ticket and a paragraph they remember is missing.

So `-b` also refuses a replacement that lost more than half of a body of at
least 200 bytes:

```
pidly: the new body is 180 bytes against 4200: re-run with -f if that is
       deliberate
```

The numbers are arbitrary and stated rather than tuned. The point is to catch
a reconstruction that dropped most of the file, not to police editing, and
`-f` is there for the times a body really is being cut down.

By hand it is your editor, or `cat >> .pidly/7/info` — nothing records where
a body starts or ends, so appending is appending. What the command adds is the
lock, so an edit and a claim landing together cannot lose each other, and a
refusal to install a saved file that is no longer a ticket: a missing header
line, a field without a colon, a body that lost the blank line in front of
it. A rejected edit is kept, and the path is printed.

Fields are lines, so a one-off is `sed`, and the commands that write one for
you are:

```sh
pidly set 7 effort M          # write a field
pidly set 7 effort            # clear it, unless the schema requires a value
pidly release -m "..." 7      # the one that matters: it writes handoff
pidly fields                  # give every ticket a slot for every declared field
```

`title` and `needs` are not schema fields — the schema declares what a
project wants, and lines 1 to 3 are what a ticket *is* — but retitling and
re-wiring a dependency are ordinary work, so `set` writes them too:

```sh
pidly set 7 title "What it turned out to be about"
pidly set 7 needs "3 8"       # replace the line
pidly needs 7                 # what it needs, one a line
pidly needs -a 24 7           # add one, without retyping the others
pidly needs -d 3 7            # drop one
```

By hand these are `sed -i '3s/.*/title: .../'` and `sed -i '2s/.*/needs: 24/'`,
and they still are. What the command adds is the one thing `sed` cannot do:
**it refuses a dependency on a ticket that does not exist**, and on the ticket
itself. A `needs` naming a number nothing resolves is otherwise a `check`
finding that surfaces in CI, long after whoever wrote it has gone.

`claim` is line 1 and `set` refuses it: it is written by `claim`, `release`
and `reap`, which know what it means.

`fields` is the migration for a stanza added to the schema after tickets
already exist. It **adds keys and nothing else**: it never drops a field the
schema stopped declaring, because that is data; it never moves a line that is
already there, because a ticket written by hand may order its fields however
it likes; and it does not bump `updated`, because a migration is not activity
on the work and stamping every ticket would flatten `list --stale` on the day
it ran. A missing key lands in schema order relative to the keys that are
present. It is never part of `init`.

`check` reports the same drift — `note: 12 ticket(s) have no 'area' line` —
which is what `fields` would add, from the command that changes nothing. It
is a **note**: printed, but it does not fail `check`. A ticket written by
hand is a legal ticket and will not carry every slot, and the format's own
promise is that mkdir and an editor are enough.

## Delegating to a subagent

A subagent usually shares its parent's process — under Claude Code, a Bash
call from a subagent reports the same `CLAUDE_PID` as the lead agent. So a
pid cannot tell them apart: two claims, one pid, both live. **A subagent
claims as an agent, with a lease**, the same way a cloud agent does:

```sh
PIDLY_AGENT=sub-review-parser PIDLY_LEASE=1h pidly claim 19
```

The lead agent creates the ticket and passes the number down, because it
writes the subagent's prompt:

```sh
pidly new -p 7 "Review the parser changes"     # prints 19
# ...then include "your ticket is 19" in the subagent's instructions
```

When the subagent finishes it leaves a handoff and releases; the lead reads
that and decides whether to close. If the subagent dies, the lease expires
and the ticket frees itself.

**Write down what the subagent found before the context is gone.** Its
output is otherwise ephemeral: it lands in the lead agent's context, gets
summarised, and disappears. Findings go in the body of the ticket the
subagent worked on. Appending to a body is just appending.

If the result is a standalone artifact — a review, a benchmark — put it
where artifacts live in the repo and reference the path from the body. It is
usually about the code rather than about the ticket, so it belongs next to
the code, where everyone finds it and where closing the ticket does not
archive it.

Not a ticket of its own. One created and closed in the same breath is a log
entry wearing a ticket costume, and it spends a number that can never be
reused.

**Not every subagent deserves a ticket.** A lookup or a search does not.
Numbers are never reused and tickets are never deleted, so a ticket per
subagent call is permanent noise — and an open child blocks its parent from
closing, so it does active harm. Open one when the work is a unit you would
want to see in the tracker tomorrow.

## Closing and reopening

Closing is a move into the container's `c/`:

```sh
pidly close 12    # or: mkdir -p .pidly/7/c && mv .pidly/7/12 .pidly/7/c/
pidly reopen 12
```

A ticket **cannot close while it has children outside its own `c/`**. That is
what keeps a finished tree from containing live work.

`reopen` moves it back, and **cascades upward**: if a closed ancestor holds
it, that ancestor reopens too, one move per level. If a subtask needs redoing
then its parent is not finished either. Reopening does not cascade downward,
and does not reopen tickets that `needs` it.

Reopen also takes a ticket that is *already open* but sits inside a closed
ancestor — a state a hand-run `mv` can leave behind, and one `check` reports.
The cascade is its repair.

## Re-parenting

Moving a ticket under a different parent is a move, and by hand it is one:

```sh
mv .pidly/1/17 .pidly/6/17        # and it works
pidly reparent 17 6               # what it is for
pidly reparent -r 17              # out to the top
```

`needs` holds numbers and the registry keys on numbers, so dependencies and
identity survive a move untouched; only the hierarchy is positional. The
command exists for the one case `mv` gets **quietly** wrong.

Every other thing you can do by hand fails loudly — a bad field fails `check`,
a botched line 3 stops parsing. Moving a ticket across a `c/` boundary fails
silently, and in the direction that loses work: drop a closed parent back into
the open tree and everything under it is open again, with `check` content and
nothing recording that it happened.

So the rule is that **a reparent never changes whether a ticket is closed**. A
closed ticket lands in the new parent's `c/` and stays closed; an open one
lands directly under it. A closed destination is refused, and so is a parent
inside the ticket's own subtree, and so is an open ticket stranded inside a
closed ancestor — that last one is `check`'s finding and `reopen`'s repair,
and moving it would only hide it.

## Rules that will bite you

- **Never delete a ticket.** Numbers are never reused, and deleting one lets
  its number be issued again to something else. Close it instead.
- **`needs` holds numbers, never paths.** A number is permanent; a path
  changes every time a ticket is closed or re-parented.
- **Parents and dependencies are different things.** `needs` blocks starting;
  children block closing. Neither implies the other, and a parent is never an
  implicit dependency of its own children.
- **Leave a handoff when you stop early.** A dropped claim with no note makes
  the next agent reconstruct your progress from the diff.
